# ReqFlow 产品总纲

> 版本：v0.5 · 维护者：接手开发者 · 本文是产品层面的「宪法」，技术细节见 [HANDOVER.md](./HANDOVER.md)

## 1. 一句话定位

**ReqFlow 是 Task 生命周期管理与 AI agent loop 驱动的综合性项目管理辅助平台**：把项目管理中范式统一、重复度高、人力密集的工作环节（需求拆解、缺陷定级、批量整理…），抽离成定制化的 AI 驱动 Task——用定制化 Task 流程 + AI agent 任务专属工具替代重复劳动；**任务与任务通过数据集衔接**（需求导入产出需求数据集，Bug 分析等后续任务以它为输入），形成「任务 + 数据」的业务闭环。AI 基于原文执行与起草（分批阅读、分批产出、必要时问人），人负责把关与决策，把生产力从机械劳作中解放出来。

## 2. 背景与问题

项目管理中大量工作环节具备三个共性：

| 共性 | 表现 |
|------|------|
| 范式统一 | 输入输出结构稳定、处理规则明确，本质上是一页纸就能写清的 SOP |
| 重复度高 | 按版本、按轮次、按批次反复发生 |
| 人力密集 | 耗时、需跨系统查证（查历史、查结果集、查元数据）或需逐条处理 |

典型场景：需求文档逐条拆需求并查重归类、Bug 反馈汇总定级并关联需求、多轮迭代的数据整理……这些环节消耗团队大量工时，却几乎不产生决策价值。真正的价值在判断——拆得对不对、该不该收录、定几级——而不在抄录与搬运。AI 能起草与查证，但审批必须留给人。

ReqFlow 的答案：**用定制化 Task 流程 + AI agent 任务专属工具，把这些环节从「人手逐条处理」变为「AI 起草 + 人工把关」**。

## 3. 核心范式：一个重复人工任务如何抽离成 AI 驱动 Task

平台的核心能力不是某个具体功能，而是这套可复制的抽离范式——每个新任务类型都按以下五步立项、设计、落地。

### 3.1 识别：这个环节值不值得抽离

三个判据同时满足才是候选：

| 判据 | 检验方法 |
|------|---------|
| 范式统一 | 能否写出一页纸 SOP？输入输出结构是否稳定？ |
| 重复度高 | 是否按版本 / 轮次 / 批次反复发生？ |
| 人力密集 | 是否耗时、需跨系统查证、需逐条处理？ |

直觉检验：新同学按 SOP 两周能上手、团队每周都在做——就是候选。

### 3.2 拆解：把 SOP 变成 Task 步骤链

人工 SOP 的每个自然阶段 = 一个步骤。步骤是 Task 的最小可观测单元：

- **机器执行步骤**：解析、LLM 生成、查证、批量写入——交给 agent 执行；
- **人工确认门（Gate）**：花钱前（LLM 调用）、写操作前（数据集生成）、终稿前——人必须过目。

每一步的状态、进度、产物**逐条落库**——步骤时间线即 SOP 的执行记录，可回放、可审计、可续跑。

### 3.3 工具化：为任务类型定制 agent 专属工具

分析步骤的过程动作，包装成 agent 可自主调用的工具（pi 工具模式）：

- **过程工具**：分批读取文档（read_document，行号分页 + 续读提示）、正则检索定位（search_document）——AI 自主阅读原文而不是被喂全文；
- **草稿工具**（write_work_items）：分批产出结构化草稿，同 key 覆盖可修订——写的是内存草稿，落库仍走人工门；
- **交互工具**（ask_human）：关键决策点 / 卡点向人工提问（可附候选项），阻塞等待回答——判断权留在人；
- **持久写入**（数据集生成 / 条目写入）：不做自主工具——执行由人工在任务门内点击触发。

工具设计遵循 pi 成熟模式：参数 Schema 极简且内嵌真实限制常量（描述与行为同源）；执行结果拆分 Output（回传模型）与 Details（展示给 UI）；输出截断必附「怎么继续」的可行动提示。

**提示词零固定模板，按任务类型动态装配**（三处同源，不漂移）：

| 提示词段 | 数据源 |
|---|---|
| 角色指令头（角色/任务/分析要点） | 任务类型的装配描述注册表（AnalyzeProfile） |
| 草稿字段规范 | 产出数据集的 schema 渲染——字段增删改，提示词与写入校验、数据集分桶同步生效 |
| 工具使用指南 | 实际注入的工具集（每个工具自带 snippet/guidelines）——工具增删自动跟随 |

### 3.4 兜底：长程任务必须可中断、可续跑

AI 驱动的任务是长程的，必然被打断（开会、下班、服务重启）：

- **会话检查点**：agent 会话（Context）全量可序列化——暂停即落库，继续即回放续跑；
- **逐条幂等**：批量写操作逐条回写结果，断点续跑只处理未完成条目；
- **失败不杀任务**：步骤失败回到人工门可重试，任务始终可挽救，不轻易死亡。

### 3.5 把关：AI 是草稿机，不是审批者

所有 AI 产出默认可编辑、可确认；关键动作（建单、关联确认、写操作）必须有人点击。抽离掉的是重复劳动，保留的是人的判断。

### 3.6 实例：需求拆解导入（已按此范式落地）

| 人工流程 | 抽离后的 Task |
|---------|---------------|
| 收需求文档，逐条阅读拆解需求 | 步骤「上传解析」：docx / pdf / md / txt → 全文提取，进度实时可见 |
| 对照已有需求手工查重 | 步骤「AI 分析」：agent 经 read_document / search_document 自主阅读原文，write_work_items 分批产出草稿，关键决策点 ask_human 问人（工具轨迹与人工交互全程可见） |
| 人工录入标题 / 优先级 / 工时 / 负责人 | 人工门「确认解析」：花钱前修正解析噪音、注入额外要求 |
| 逐条录入系统 / 与已有需求比对 | 人工门「生成数据集」：查重徽标 + 行内编辑 → 命名数据集并生成（向量化写入），产出可供后续任务消费的结果集 |
| — | 全流程 Task 化：创建 / 暂停 / 继续 / 完成 + 步骤时间线回放 |

### 3.7 复制：范式随任务类型沉淀

跑通一个任务类型后，同构环节（Bug 定级、汇总…）按同一范式复制：**新类型 = 新步骤链 + 新工具集 + 复用生命周期底座**，边际成本随任务类型数量递减。这是平台「辅助」属性的来源——不是一次性工具，而是可生长的工作台。

## 4. 方向性决策（架构演进的主线，改前必读）

以下决策是历次演进沉淀的「为什么」，新功能不得违背，变更必须显式推翻并记录。

### 决策一：一切长程流程必须有 Task 身份（任务化）

**决策**：所有持续超过一次交互的工作（解析、分析、批量写入、跨任务衔接）都以 Task 实体承载，配完整生命周期（创建 / 列表 / 详情 / 编辑 / 暂停 / 继续 / 完成终态），执行脱离 HTTP 请求（独立 goroutine + 可取消 ctx）。

**为什么**：无 Task 身份时，长程流程的状态只存在于瞬时请求中——切页即失联、刷新即重跑、崩溃即卡死。任务化后：进度落库可回放、执行与页面解耦（断开照跑）、服务重启自动标暂停可继续。

**约束**：状态机恒为 `pending → running → awaiting | paused → running → succeeded | failed`；每任务单写者（状态落库只有一个执行 goroutine）；触发一律 fire-and-forget，客户端经 `/events` 订阅进度。

### 决策二：半元数据驱动（workflow 注册表 + StepKind 分发）

**决策**：任务类型定义 = 一份**半元数据工作流**（步骤链 + 每步依赖声明，`Workflow{Steps[{Seq,Name,Kind,Deps}]}`），创建任务时快照进 `tasks.workflow`；执行引擎按 `StepKind`（parse / human / analyze / dataset）查注册的执行器分发。**不做全配置化**——执行器仍是有类型的 Go 代码，只有「步骤长什么样、依赖什么」是数据。

**为什么**：
- 全配置化（DSL / 外置定义）在只有 2-3 个任务类型时是过度抽象——执行逻辑终究要写代码；
- 半元数据让**新增任务类型 = 一条注册表定义 + 复用/新增 kind 执行器**，分发与推进（canTriggerStep / advanceGate）不再感知具体类型；
- 快照进任务（而非运行时查注册表）使任务自描述、历史任务不受定义演进影响。

**约束**：新增任务类型必须走注册表，禁止在 runner 里堆 `if type == …`；StepKind 是封闭集合，新增种类需同时注册执行器与门推进语义。

### 决策三：剪除外部分平台，数据集驱动闭环（去平台化）

**决策**：不依赖任何外部项目管理平台（已全量剪除 PingCode）。任务间通过**数据集**衔接：任务产出结果集（需求数据集 / Bug 数据集…），后续任务以数据集为输入（关联匹配、查证、定级底料）。平台数据只在本平台内流转，不对外部平台写数据。

**为什么**：
- 外部平台的同步 / 映射 / 状态回写是巨大的维护负债，且**对「任务 + 数据」闭环贡献趋近于零**——闭环的本质是任务产出结构化数据、数据被后续任务消费，这不需要第三方；
- 数据集是第一等公民（类型化条目 + 向量检索），查重 / 关联匹配 / 后续任务输入统一以此为语料——一次写入，处处复用；
- 剪除外部依赖后，升级发布 = 替换单二进制，零外部联动。

**约束**：任务消费的数据集通过 `input_dataset_id` 显式指定（缺省查全部）；写数据集的执行必须经人工门触发，agent 不得自主写。

### 决策四：AI 起草 + 人工把关，读自主 / 写把关

**决策**：读工具（文档读取/检索）与草稿工具（write_work_items 写内存草稿）agent 可自主调用；写持久存储（数据集生成、关联确认、写入）必须人工在门内点击；ask_human 把关键判断上交人工。AI 产出默认可编辑、可确认。

**为什么**：抽离的是抄录与搬运，保留的是判断。agent 工具化让 AI「基于原文出稿、分批产出、必要时问人」，人工门把「花钱」（LLM 调用）与「写操作」留在人的决策圈内。

### 决策五：单实例多客户端（当前部署边界）

**决策**：当前部署形态是单服务端进程 + 任意多客户端（浏览器），架构自始按多客户端设计（事件扇出按任务挂多订阅者、慢客户端丢帧不拖累他人、断线自动重连重收快照、状态机校验让并发操作只败不坏）。多实例水平扩展（Broker 跨进程、运行登记表跨实例）不在当前范围，是明确的未来改造点。

| Task 生命周期管理 | 创建 / 列表 / 详情 / 编辑 / 暂停 / 继续 / 完成（终态）；状态机 pending → running → awaiting \| paused → succeeded \| failed；执行脱离页面（断开照跑、重启恢复、快照回放）；触发同步预置状态（fire-and-forget 无竞态窗口） |

| 数据集管理 | 任务产出的结果集（需求数据集、Bug 数据集…）为第一等公民：类型化条目 + 向量检索；查重 / 关联匹配 / 任务间衔接的底料——**任务与任务通过数据集衔接，不依赖外部平台** |
| 实时事件流 | 进程内 Broker 扇出 + SSE（subscribe-before-snapshot 消除竞态；帧形状统一、单帧异常不断流、断线自动重连；高频 token 事件节流合并） |

## 6. 能力现状

**F1 · 需求导入任务**（✅ 已交付）：上传文档 → 解析 → 确认门 → AI 分析（agent 自主阅读文档、分批产出草稿，关键决策点问人）→ 查重确认 → 人工命名生成需求数据集；全程任务跟踪，可暂停续跑、可重放；产出数据集即后续任务的输入。

**F2 · 数据集管理**（✅ 已交付）：结果集浏览（需求集等）、条目明细、来源任务追溯；查重与关联匹配的统一语料。

**F3 · Bug 处理任务**（🔲 第二波）：Excel 导入 → 与需求数据集关联匹配（精确 / 语义 top3）→ 人工确认关联 → AI 定级 P0-P3（附理由）→ **生成 Bug 数据集**；作为新任务类型接入，全流程 AI 起草 + 人工把关，**需求数据集即其输入**（方案定稿于 `internal/app/bug/doc.go`）。

**F4 · 更多任务类型**（🔲 扩展）：按 §3 范式，把团队日常同构环节逐步抽离（定级、汇总、归档…），任务间通过数据集自由衔接。

## 8. 后续迭代指导（方向性）

### 8.1 新任务类型：接入路径

按 §3 范式立项，落地顺序固定：

1. **识别**（§3.1 三判据）→ **拆解**（§3.2 步骤链，机器步 / 人工门分列）；
2. **工具化**（§3.3）：确认查证动作与数据源——数据源优先选**已有数据集**（本地、零外部依赖），新数据源需评估是否值得成为新数据集类型；
3. **落地**：三个注册——工作流定义（`app/workflow.go` 步骤链）+ 产出数据集 schema（`model.Schemas()`，字段附提取说明）+ agent 装配描述（`app/analyze_profile.go` 指令头/绑定）——执行骨架、提示词装配、降级链零改动；复用 / 新增 StepKind 执行器（`app/runner.go` 分发）→ 前端任务详情页加工作区面板（复用 TaskDetail + panels 模式）；
4. **产出闭环**：任务的**终态产物必须是数据集**（或显式说明无产物）——没有数据产出的任务不构成闭环，等于白跑。

### 8.2 数据集体系：演进方向

- **类型化字段是数据集的契约**：每种数据集类型定义自己的字段形状（需求 = 草稿形状），字段只增不减，新增字段走迁移 + 重建；
- **衔接约定**：消费方任务用 `input_dataset_id` 指定输入数据集（缺省 = 全部同类），关联匹配 = 精确（归一化）前置 + 语义（向量）兜底，阈值按场景可配；
- **演进顺序**：先跑通 Bug 链路（消费需求集 → 产出 Bug 集），再评估「数据集版本化」「跨类型关联（Bug ↔ 需求）」——一切以任务闭环的实际需要为准，不做无消费方的数据集类型。

### 8.3 多客户端上线：路线（第三波）

单实例多客户端当前即支持；**上线前**按此顺序补：

1. **认证授权**（硬门槛）：登录 + 会话，任务 / 数据集操作校验，防止数据裸奔；
2. **LLM 并发限流**（稳定性）：信号量限制并发 LLM / embedding 调用 + 排队，防上游限流导致的「卡住 / 超时」；
3. **草稿冲突**（质量）：草稿批量替换加版本号乐观锁，后写覆盖前写显式报冲突；
4. **多实例扩展**（远期）：Broker 进程内扇出 / running 登记表 / 上传文件本地盘都是单实例绑定——扩展时分别换 Redis pub-sub / 分布式锁 / 对象存储。

### 8.4 技术演进的红线

- 读工具可自主、**写工具永远人工把关**——不松动；
- 任务状态机五态、每任务单写者——不松动；
- 新任务类型走注册表、禁 `if type ==` 堆逻辑——不松动；
- 数据只在本平台流转、不对外部平台写数据——不松动。

## 9. 产品原则

1. **Task 优先**：一切长程工作先抽象任务，再谈实现——没有任务身份的流程不允许存在；
2. **AI 提效，人工把关**：AI 产出默认可编辑、可确认，关键动作（数据集生成、关联确认、写入）必须有人点击——AI 是草稿机不是审批者；
3. **读工具自主、写工具把关**：过程工具（读取/检索/草稿写入）agent 可自主调用，数据集的生成/写入一律人工确认后执行，关键判断可上交人工（ask_human）；
4. **可中断可续跑**：长程任务必须支持暂停 / 继续 / 重放，失败回到人工门而非死亡；
5. **抑制重复**：与已有需求数据集查重是导入类任务的默认前置步骤，宁可误报「疑似重复」让人确认，不可静默重复收录；
6. **零硬编码配置**：一切端点、密钥、阈值来自本地 `config.yaml`（env 可覆盖）；
7. **优雅降级**：依赖未配置时功能按依赖关系降级（无 embedding → 仅精确匹配），服务永远能启动并明确告知缺什么；
8. **单文件交付**：`go:embed` 单二进制 + 配置文件即完整部署，降低内网分发成本。

## 10. 边界与非目标

- 不做多人协作 / 权限体系（单工作区；认证是第三波硬门槛，见 §8.3）；
- 不做文档协同编辑（只做「入口」处理，管理留在协作平台）；
- 数据只在本平台内流转（任务产出数据集、任务消费数据集），**不对外部平台写数据**（去平台化决策，见 §4 决策三）；
- 不自建 LLM 推理 / 向量服务（一律 OpenAI 兼容协议外接）；
- 不做通用 AI 助手：每个任务类型必须按 §3 范式显式抽离，拒绝「灵机一动」的临时功能——范式是平台的护城河，也是质量底线；
- 不做多实例部署（单实例多客户端为当前边界，扩展见 §8.3-4）。

## 11. 名词表

| 术语 | 含义 |
|------|------|
| Task | 长程工作的生命周期载体：类型化步骤链 + 状态机 + 检查点；可创建 / 列表 / 详情 / 编辑 / 暂停 / 继续 / 完成 |
| 步骤（Step） | 任务的最小可观测单元：机器执行或人工门，状态 / 进度 / 产物逐条落库 |
| 人工门（Gate） | 花钱前 / 写操作前 / 终稿前必须人工过目的步骤 |
| 抽离范式 | §3 五步法：识别 → 拆解 → 工具化 → 兜底 → 把关，把重复人工任务变成 AI 驱动 Task 的通用方法 |
| 半元数据工作流 | 任务类型定义 = 步骤链 + 依赖声明的注册表数据；执行器按 StepKind 分发（见 §4 决策二） |
| 任务专属工具 | 为任务类型定制的 agent 过程工具集（读取/检索/草稿写入/问人）；Output 给模型、Details 给 UI，按任务类型 profile 注入 |
| 装配描述（Profile） | 任务类型 → agent 装配的注册表映射：指令头 + 产出 schema 绑定 + 写入工具配置；提示词据此动态装配 |
| agent loop | 模型与工具交替执行的循环：有工具调用就执行并回传，无则自然终止 |
| 会话检查点 | agent 会话（Context）的 JSON 序列化：暂停续跑与换模型续跑的统一载体 |
| 两层匹配 | 归一化精确匹配 + 向量语义匹配的组合策略（精确前置保护版本号 / 工单号等关键 token） |
| 数据集 | 任务产出的结果集（需求数据集 / Bug 数据集…）：类型化条目 + 向量检索；任务间衔接的载体 |
| 任务衔接 | 任务 A 产出数据集 → 任务 B 以它为输入（如 Bug 分析消费需求数据集做关联匹配）——「任务 + 数据」闭环 |
| 查重 | 草稿与已有数据集条目的 New / Similar 判定（两层匹配：归一化精确 + 向量语义） |
| 语料库 | 全部需求数据集条目（含向量），查重 / 关联匹配的统一底料（agent 阅读的对象是任务自身的语料——如需求文档全文，经读取/检索工具按需取用） |
