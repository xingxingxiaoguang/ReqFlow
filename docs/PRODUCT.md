# ReqFlow 产品总纲

> 版本：v0.1（第一波交付后） · 维护者：接手开发者 · 本文是产品层面的「宪法」，技术细节见 [HANDOVER.md](./HANDOVER.md)

## 1. 一句话定位

**ReqFlow 是一款需求与缺陷的「入口集散」工作台**：把散落在各处的需求文档和 bug 反馈文档，经过解析、AI 分析、智能匹配与人工确认，高质量地沉淀到 PingCode 等协作平台——让团队在正式建单之前，先完成需求的梳理、去重与缺陷的定级归类。

## 2. 背景与问题

团队接入协作平台（如 PingCode）前，需求与缺陷通常以非结构化文档流转：

- **需求侧**：Word/PDF/Markdown 需求文档靠人工逐条录入工作项，慢、易漏、粒度不一，且经常把已存在的需求重复建单；
- **缺陷侧**：测试/客服的 bug 反馈多是 Excel 汇总，编号与需求对应关系模糊，优先级靠拍脑袋，导入后无法追溯到需求。

ReqFlow 的答案：**文档进、结构化出，AI 提效、人工把关、平台落库**。

## 3. 目标用户与核心场景

| 用户 | 场景 | 使用频率 |
|------|------|---------|
| 项目经理 / 产品 | 版本规划期批量导入需求文档，梳理为工作项 | 按版本迭代 |
| 测试负责人 | 回归后批量导入 bug 反馈 Excel，确认与需求的关联并定级 | 按测试轮次 |
| 团队管理员 | 配置平台连接与模型，维护同步数据 | 一次性 / 低频 |

产品形态：**本机或内网部署的单工作区工具**（单二进制 + 本地配置文件），不是多租户 SaaS。

## 4. 功能全景

### 4.1 核心功能（四大件）

**F1 · 需求文档批量解析导入**（✅ 第一波已交付）

上传 docx / pdf / md / txt → 解析确认门（预览修正全文）→ LLM 流式分析为结构化工作项（项目分组、标题、描述、优先级、预估工时、负责人、解决方案建议）→ 项目推荐 + 同项目查重（New/Similar）→ 人工编辑确认 → SSE 批量建单到 PingCode（支持自动创建新项目）。

**F2 · Bug 反馈文档导入与需求关联**（🔲 第二波）

上传 bug Excel → 行级解析为结构化 bug → **有编号**：按编号与已同步工作项精确匹配；**无编号**：语义匹配取 top3 候选 → 匹配度过低判为无效 bug → top3 经**人工确认**建立/否决关联 → 确认关联的 bug 同步到平台缺陷管理。

**F3 · Bug 批量 AI 定级**（🔲 第二波）

对 bug 批量 LLM 分析，定四档优先级并给出理由：

| 档位 | 定义 |
|------|------|
| **P0** | 阻塞性——主流程不可用、数据丢失/损坏、安全漏洞，立即修复 |
| **P1** | 核心功能性——核心功能错误但有绕行方案，本迭代内修复 |
| **P2** | 次要功能性——边缘场景问题、体验缺陷，排期修复 |
| **P3** | 边缘性——趋近无效（无法复现/描述不清/极低频），观察或关闭 |

**F4 · 多协作平台同步**（✅ PingCode 已实现，多平台为扩展方向）

增量同步平台项目/工作项/元数据到本地语料库（关系 + 向量），为匹配与查重提供底料。三态同步：新增 / 更新 / 软归档。

### 4.2 支撑能力

- **两段式确认门**：解析与 LLM 分析分离，用户在花钱的 LLM 调用前修正解析噪音，并可注入「额外要求」；
- **两层匹配策略**：归一化精确匹配前置（保护版本号/工单号等关键 token 不被向量稀释），语义向量兜底「换了说法」的近似；
- **导入记录与恢复**：每轮分析导入全程留痕，可回填向导继续编辑；
- **密钥安全护栏**：四道防线防止 API key 随代码分享泄漏（详见 HANDOVER §9）。

## 5. 产品原则

1. **AI 提效，人工把关**：所有 AI 产出（分析结果、匹配关系、定级）默认可编辑/可确认，关键动作（导入、关联确认）必须有人点击——AI 是草稿机不是审批者；
2. **抑制重复**：与平台已有数据查重是导入的默认前置步骤，宁可误报「疑似重复」让人确认，不可静默重复建单；
3. **零硬编码配置**：一切端点、密钥、阈值来自本地 `config.yaml`（env 可覆盖），代码与打包产物不含任何配置值；
4. **优雅降级**：密钥未配置时功能按依赖关系降级（无 embedding→仅精确匹配；无 MinerU→PDF 不可用但 docx 不受影响），服务永远能启动并明确告知缺什么；
5. **单文件交付**：`go:embed` 单二进制 + 配置文件即完整部署，降低内网分发成本。

## 7. 边界与非目标（当前版本明确不做）

- 不做多人协作/权限体系（单工作区；auth 扩展点已留）；
- 不做需求文档的版本管理与协同编辑（只做「入口」，管理留在协作平台）；
- 不直接写操作平台的存量工作项（只创建新项；更新已有项的 API 能力已具备但未开放 UI）；
- 不自建 LLM 推理/向量服务（一律 OpenAI 兼容协议外接）。

## 8. 名词表

| 术语 | 含义 |
|------|------|
| 确认门（Gate） | LLM 分析前的全文预览/编辑步骤 |
| 草稿（Draft） | LLM 分析产出、尚未导入平台的工作项 |
| 查重（Duplicate Check） | 草稿与已同步工作项的 New/Similar 判定 |
| 语料库 | 本地同步缓存的平台项目/工作项（含向量），匹配的底料 |
| 两层匹配 | 归一化精确匹配 + 向量语义匹配的组合策略 |
| 软归档 | 平台侧已删除的条目在本地标记 `is_archived` 而非物理删除 |
| 优先级档位 | Bug 定级专用：P0/P1/P2/P3（区别于工作项自身的 High/Medium/Low 优先级字段） |
