# ReqFlow 产品总纲

> 版本：V2（未上线重构版） · 维护者：接手开发者 · 本文是产品层面的「宪法」，技术细节见 [HANDOVER.md](./HANDOVER.md)

## 1. 一句话定位

**ReqFlow 是以不可变数据、可复用流程定义和可追溯执行任务为核心的无代码 AI 数据管线平台**：业务人员通过可视化编排把资料清洗入库、建立精准 + 语义索引，再让 Agent 在固定知识边界内查询、分析并生成制品。AI 负责读取、抽取和起草，人负责审核与发布；流程定义负责“怎么做”，任务负责“这一次执行”，数据集负责跨任务衔接。

当前产品只采用 V2 模型。项目尚未上线，不兼容旧数据、旧 API、旧页面或旧任务流程；文档中的 Legacy 内容仅用于识别待删除代码，不得作为新功能设计依据。

## 2. 背景与问题

项目管理中大量工作环节具备三个共性：

| 共性 | 表现 |
|------|------|
| 范式统一 | 输入输出结构稳定、处理规则明确，本质上是一页纸就能写清的 SOP |
| 重复度高 | 按版本、按轮次、按批次反复发生 |
| 人力密集 | 耗时、需跨系统查证（查历史、查结果集、查元数据）或需逐条处理 |

典型场景：需求文档逐条拆需求并查重归类、Bug 反馈汇总定级并关联需求、多轮迭代的数据整理……这些环节消耗团队大量工时，却几乎不产生决策价值。真正的价值在判断——拆得对不对、该不该收录、定几级——而不在抄录与搬运。AI 能起草与查证，但审批必须留给人。

ReqFlow 的答案：**用定制化 Task 流程 + AI agent 任务专属工具，把这些环节从「人手逐条处理」变为「AI 起草 + 人工把关」**。

## 3. 核心范式：把重复业务工作变成可复用流程

平台的核心能力不是某个固定任务模板，而是把 SOP 编排为 `TaskDefinition`，再从定义派生任意数量 `Task` 的能力。模板只是可编辑的定义起点；业务人员也可以从空白组合已注册 Executor、连接类型匹配的数据端口并发布流程。

```text
可编辑模板 / 空白编排 → TaskDefinition（流程定义）
                              ↓ 1:N 派生
                      Task（一次执行实例）
                              ↓
               StepRun + Resource Boundary + Output
```

### 3.1 识别：这个环节值不值得抽离

三个判据同时满足才是候选：

| 判据 | 检验方法 |
|------|---------|
| 范式统一 | 能否写出一页纸 SOP？输入输出结构是否稳定？ |
| 重复度高 | 是否按版本 / 轮次 / 批次反复发生？ |
| 人力密集 | 是否耗时、需跨系统查证、需逐条处理？ |

直觉检验：新同学按 SOP 两周能上手、团队每周都在做——就是候选。

### 3.2 拆解：把 SOP 变成 Task 步骤链

人工 SOP 的每个自然阶段 = 一个步骤。步骤是 Task 的最小可观测单元：

- **机器执行步骤**：解析、LLM 生成、查证、批量写入——交给 agent 执行；
- **人工确认门（Gate）**：花钱前（LLM 调用）、写操作前（数据集生成）、终稿前——人必须过目。

每一步的状态、进度、产物**逐条落库**——步骤时间线即 SOP 的执行记录，可回放、可审计、可续跑。

### 3.3 工具化：为任务类型定制 agent 专属工具

分析步骤的过程动作，包装成 agent 可自主调用的工具（pi 工具模式）：

- **过程工具**：分批读取文档（read_document，行号分页 + 续读提示）、正则检索定位（search_document）——AI 自主阅读原文而不是被喂全文；
- **草稿工具**（write_work_items）：分批产出结构化草稿，同 key 覆盖可修订——写的是内存草稿，落库仍走人工门；
- **交互工具**（ask_human）：关键决策点 / 卡点向人工提问（可附候选项），阻塞等待回答——判断权留在人；
- **持久写入**（数据集生成 / 条目写入）：不做自主工具——执行由人工在任务门内点击触发。

工具设计遵循 pi 成熟模式：参数 Schema 极简且内嵌真实限制常量（描述与行为同源）；执行结果拆分 Output（回传模型）与 Details（展示给 UI）；输出截断必附「怎么继续」的可行动提示。

#### 平台数字大脑

`/agent` 是产品默认首页。它复用同一套 pi 式 loop，但服务于跨模块的平台操作，而不是某个 Task 的单步骤分析：会话完整落库，可刷新恢复、停止当前回答并继续提问；默认提供 4 个可独立启停的只读平台工具——平台使用规则（platform_guide）、流程查询、任务查询和数据查询/检索。

Skill 是工作区级纯文本提示词模块，不包含脚本、附件或依赖。聊天框输入 `/` 会列出已激活 Skill；选定后完整提示词只注入本轮，同时继承系统安全边界与当前工具权限。设置模块可创建、停用和激活 Skill。

数字大脑是只读使用顾问：依据 `platform_guide` 返回的平台使用规则，指导用户在页面上搭建流程、创建与运行任务、建立数据索引，并基于平台真实数据做查询与分析。它没有创建、修改、运行或发布类工具，不直接写 Dataset Item、伪造资源 ID 或绕过人工 Gate；写动作一律由用户在页面完成，Agent 负责事前指引与事后核实。

**提示词零固定模板，按任务类型动态装配**（三处同源，不漂移）：

| 提示词段 | 数据源 |
|---|---|
| 角色指令头（角色/任务/分析要点） | 任务类型的装配描述注册表（AnalyzeProfile） |
| 草稿字段规范 | 产出数据集的 schema 渲染——字段增删改，提示词与写入校验、数据集分桶同步生效 |
| 工具使用指南 | 实际注入的工具集（每个工具自带 snippet/guidelines）——工具增删自动跟随 |

### 3.4 兜底：长程任务必须可中断、可续跑

AI 驱动的任务是长程的，必然被打断（开会、下班、服务重启）：

- **会话检查点**：agent 会话（Context）全量可序列化——暂停即落库，继续即回放续跑；
- **逐条幂等**：批量写操作逐条回写结果，断点续跑只处理未完成条目；
- **失败不杀任务**：步骤失败回到人工门可重试，任务始终可挽救，不轻易死亡。

### 3.5 把关：AI 是草稿机，不是审批者

任务内 AI 产出默认可编辑、可确认；业务数据发布、审核决定等关键动作必须经过人工 Gate。首页数字大脑可以把用户在会话中明确下达的“创建/运行”指令转换为平台用例调用，但不能替用户作出未表达的业务审核决定。抽离掉的是重复劳动，保留的是人的判断。

### 3.6 历史实例：Legacy 需求拆解导入（仅供范式参考）

| 人工流程 | 抽离后的 Task |
|---------|---------------|
| 收需求文档，逐条阅读拆解需求 | 步骤「上传解析」：docx / pdf / md / txt → 全文提取，进度实时可见 |
| 对照已有需求手工查重 | 步骤「AI 分析」：agent 经 read_document / search_document 自主阅读原文，write_work_items 分批产出草稿，关键决策点 ask_human 问人（工具轨迹与人工交互全程可见） |
| 人工录入标题 / 优先级 / 工时 / 负责人 | 人工门「确认解析」：花钱前修正解析噪音、注入额外要求 |
| 逐条录入系统 / 与已有需求比对 | 人工门「生成数据集」：查重徽标 + 行内编辑 → 命名数据集并生成（向量化写入），产出可供后续任务消费的结果集 |
| — | 全流程 Task 化：创建 / 暂停 / 继续 / 完成 + 步骤时间线回放 |

### 3.7 复制：范式随任务类型沉淀

跑通一个业务流程后，同构环节按同一范式沉淀为新的 `TaskDefinition`：优先复用现有 Executor、Profile 和资源类型，只有通用平台能力无法表达时才开发新 Executor。边际成本随可复用能力增加而递减。

## 4. 方向性决策（架构演进的主线，改前必读）

以下决策是历次演进沉淀的「为什么」，新功能不得违背，变更必须显式推翻并记录。

### 决策一：定义与执行必须分离

**决策**：`TaskDefinition` 是可复用、端口化的 DAG，定义步骤、依赖、输入输出端口和 Executor 配置；`Task` 只能从 `active` Definition 派生，表示一次具体执行。发布流程与创建任务是两个独立动作，一个 Definition 可以派生多个 Task。

**为什么**：定义和执行混在一个“任务类型模板”页面中，会让复用、版本、资源边界和运行历史失去清晰归属。分离后，流程可以独立设计和发布，任务可以冻结当次执行合同并安全运行。

**约束**：前端不得在创建 Task 时隐式创建或修改 TaskDefinition；发布 Definition 不得自动创建 Task。Task 创建时必须冻结完整 Definition Snapshot、输入 ResourceBinding、Dataset/Retrieval 读取边界和每个步骤的 StepRun。

### 决策二：外置 TaskDefinition + 类型化 Executor

**决策**：流程定义是持久化的一等资源，步骤通过稳定 `step_id` 组成 DAG，输入只引用 `$task.<port>` 或 `$step.<step_id>.<port>`。执行能力由封闭的 Executor Kind 集合提供，Executor 仍是有类型的 Go 代码；无代码编排只组合已注册能力，不执行任意脚本、任意表达式或未知配置。

**为什么**：
- 外置 Definition 让业务流程可以无代码复用、审阅和独立发布；
- 类型化 Executor 让数据库事务、资源身份、权限边界和恢复语义仍由代码保证；
- Definition Snapshot 让任务自描述，不受后续流程演进影响。

**约束**：模板只生成可编辑 Definition 草案/UI 状态，不是业务任务类型实体。步骤依赖必须由类型匹配的数据连接推导；新增 Executor Kind 必须同时实现输入输出合同、配置表单、恢复/幂等语义和测试，禁止在 Orchestrator 状态机中增加业务类型分支。

### 决策三：剪除外部分平台，数据集驱动闭环（去平台化）

**决策**：不依赖任何外部项目管理平台（已全量剪除 PingCode）。任务间通过**数据集**衔接：任务产出结果集（需求数据集 / Bug 数据集…），后续任务以数据集为输入（关联匹配、查证、定级底料）。平台数据只在本平台内流转，不对外部平台写数据。

**为什么**：
- 外部平台的同步 / 映射 / 状态回写是巨大的维护负债，且**对「任务 + 数据」闭环贡献趋近于零**——闭环的本质是任务产出结构化数据、数据被后续任务消费，这不需要第三方；
- 数据集是第一等公民（类型化条目 + 向量检索），查重 / 关联匹配 / 后续任务输入统一以此为语料——一次写入，处处复用；
- 剪除外部依赖后，升级发布 = 替换单二进制，零外部联动。

**约束**：任务消费的数据集或 Retrieval Snapshot 必须通过 Definition 输入端口显式绑定，并在创建时固化读取边界；写 Dataset Batch、发布 Artifact 等正式操作必须经过显式审核策略，Agent 不得绕过发布 Executor 自主写入。

### 决策四：AI 起草 + 人工把关，读自主 / 写把关

**决策**：任务内分析 Agent 的读工具（文档读取/检索）与草稿工具（write_work_items 写内存草稿）可自主调用；业务数据发布、关联确认与审核决定必须由人工 Gate 把关。首页数字大脑是平台控制面：用户明确要求后可创建流程、创建/运行任务和发起索引任务，但一律经过正式用例与 Orchestrator，不拥有直接写业务数据的旁路。ask_human 把任务内关键判断上交人工，AI 产出默认可编辑、可确认。

**为什么**：抽离的是抄录与搬运，保留的是判断。agent 工具化让 AI「基于原文出稿、分批产出、必要时问人」，人工门把「花钱」（LLM 调用）与「写操作」留在人的决策圈内。

### 决策五：单实例多客户端（当前部署边界）

**决策**：当前部署形态是单服务端进程 + 任意多客户端（浏览器），架构自始按多客户端设计（事件扇出按任务挂多订阅者、慢客户端丢帧不拖累他人、断线自动重连重收快照、状态机校验让并发操作只败不坏）。多实例水平扩展（Broker 跨进程、运行登记表跨实例）不在当前范围，是明确的未来改造点。

|------|------|

| Task 生命周期管理 | 从 active Definition 派生执行实例，创建时冻结定义快照、资源绑定和读取边界；支持启动、暂停、继续、人工审核、失败重试和终态回放 |
| 持久化 Orchestrator | Executor Registry + ready-set Scheduler + 可配置固定协程池 + PostgreSQL Worker/lease/checkpoint/fencing；单实例默认同时执行 6 个 StepRun，StepRun 是执行事实源，SSE 只负责通知 UI |

| 混合检索 | OpenSearch BM25 + pgvector Vector + 查询级权重、阈值、召回数和加权 RRF；可选 SiliconFlow rerank 并控制 top N |
| 元数据与资源目录 | Schema/Profile 使用面向业务用户的可视化表单；结构和合同变化创建新版本资源，不直接暴露 JSON 作为主操作界面 |
| 无代码业务任务 | 数据清洗、索引构建、Bug 分析、产品方案和知识图谱以可编辑模板起步，也支持从空白编排；业务差异进入 Profile、资源绑定和 Definition |
| 部署形态 | 单机 2c2g 单二进制（内嵌前端）+ PG/pgvector 单容器，零重型组件；升级 = 替换文件重启 |

## 6. 能力现状

**数据清洗入库**（✅）：AssetSet → 解析 → Schema 驱动抽取 Agent（可自纠错、可实时观察工具链）→ 确定性转换/校验 → 人工审核 → Dataset Batch 原子发布。

**精准 + 语义索引**（✅）：Base Dataset 增量派生 Query Dataset，构建覆盖相同数据边界的 BM25 + Vector Retrieval Snapshot。

**查询与分析**（✅）：在 KnowledgeScope 内执行混合检索和 Agent 分析，保留排名证据、原始 provenance、模型和 Profile 边界。

**业务制品**（✅）：Bug 分析、产品方案生成和知识图谱构建复用通用 Executor，不存在业务专用 Runner。

**数字大脑首页**（✅）：持久会话统一调用流程、任务和数据能力，支持停止、刷新恢复、继续编辑、可追踪工具执行、工具权限开关和纯文本 Skill。

**纯 V2 前端**（✅）：一级路由收敛为数字大脑、流程管理、数据管理、任务管理和归档管理，业务请求全部使用 `/api/v2`。

## 8. 后续迭代指导（方向性）

### 8.1 新业务流程：接入路径

按 §3 范式立项，落地顺序固定：

1. **识别与拆解**：把 SOP 拆成机器步骤、人工 Gate、输入资源和终态输出。
2. **优先无代码编排**：从 `/definitions/new` 空白编排，复用现有 Executor 和 Profile；五种模板只作为可编辑起点。
3. **连接数据端口**：由输入/输出资源类型选择合法来源并自动推导依赖，显式选择 Definition 输出，禁止手写任意 DAG JSON。
4. **发布与运行分离**：发布 active TaskDefinition 后，进入独立任务创建页绑定本次资源；创建任务不会修改流程。
5. **只在平台能力缺失时开发**：现有 Executor 无法表达通用能力时才新增 Kind；不得为某个业务流程复制 Runner 或向状态机加入业务分支。

### 8.2 数据集体系：演进方向

- **结构不可变**：Dataset 绑定创建时的 Schema 和 `key_fields`；结构变化创建新 Schema + 新 Dataset，不做原地兼容编辑。
- **增量写入**：业务数据通过不可变 DatasetBatch 追加，已提交 Item 不 UPDATE/DELETE；读取方使用 `dataset_id + through_seq` 固化边界。
- **检索分层**：Base Dataset 是业务事实，Query Dataset 是可检索语义单元，Retrieval Snapshot 是特定数据边界的 BM25/Vector 派生服务资源。
- **衔接约定**：消费方通过 Definition 输入端口声明资源类型，Task 创建时绑定具体 Dataset Boundary 或 Retrieval Snapshot，不使用隐式“查全部”语义。

### 8.3 多客户端上线：路线（第三波）

单实例多客户端当前即支持；**上线前**按此顺序补：

1. **认证授权**（硬门槛）：登录 + 会话，任务 / 数据集操作校验，防止数据裸奔；
2. **LLM 并发限流**（稳定性）：信号量限制并发 LLM / embedding 调用 + 排队，防上游限流导致的「卡住 / 超时」；
3. **草稿冲突**（质量）：草稿批量替换加版本号乐观锁，后写覆盖前写显式报冲突；
4. **多实例扩展**（远期）：Broker 进程内扇出 / running 登记表 / 上传文件本地盘都是单实例绑定——扩展时分别换 Redis pub-sub / 分布式锁 / 对象存储。

### 8.4 技术演进的红线

- 任务内业务发布永远经过人工 Gate；数字大脑的控制面写动作必须来自用户明确指令并经过正式用例——不松动；
- Definition 与 Task 分离、任务创建冻结快照和资源边界——不松动；
- StepRun/数据库是执行事实源，Broker/SSE 只做通知——不松动；
- 新业务优先组合现有 Executor，禁 `if type ==` 堆逻辑——不松动；
- 数据只在本平台流转、不对外部平台写数据——不松动。

## 9. 产品原则

1. **先定义、后执行**：重复 SOP 先沉淀为可复用 TaskDefinition，再派生 Task；流程设计和任务运行不得混成同一实体；
2. **AI 提效，人工把关**：AI 产出默认可编辑、可确认，关键动作（数据集生成、关联确认、写入）必须有人点击——AI 是草稿机不是审批者；
3. **读工具自主、写工具把关**：过程工具（读取/检索/草稿写入）agent 可自主调用，数据集的生成/写入一律人工确认后执行，关键判断可上交人工（ask_human）；
4. **可中断可续跑**：长程任务必须支持暂停 / 继续 / 重放，失败回到人工门而非死亡；
5. **边界可追溯**：每次读取 Dataset/Retrieval 都冻结数据边界，每个产出保留来源资源与步骤 provenance；
6. **零硬编码配置**：一切端点、密钥、阈值来自本地 `config.yaml`（env 可覆盖）；
7. **优雅降级**：依赖未配置时功能按依赖关系降级（无 embedding → 仅精确匹配），服务永远能启动并明确告知缺什么；
8. **单文件交付**：`go:embed` 单二进制 + 配置文件即完整部署，降低内网分发成本。

## 10. 边界与非目标

- 不做多人协作 / 权限体系（单工作区；认证是第三波硬门槛，见 §8.3）；
- 不做文档协同编辑（只做「入口」处理，管理留在协作平台）；
- 数据只在本平台内流转（任务产出数据集、任务消费数据集），**不对外部平台写数据**（去平台化决策，见 §4 决策三）；
- 不自建 LLM 推理 / 向量服务（一律 OpenAI 兼容协议外接）；
- 不做无边界的通用 AI 助手：每个业务流程必须声明输入、输出、知识范围和审核点；
- 不做多实例部署（单实例多客户端为当前边界，扩展见 §8.3-4）。

## 11. 名词表

| 术语 | 含义 |
|------|------|
| TaskDefinition（流程定义） | 可复用的端口化 DAG：声明输入/输出端口、步骤、依赖和 Executor 配置；发布流程不会创建任务 |
| Task（任务） | 从一个 active TaskDefinition 派生的一次执行实例；冻结定义快照和本次资源边界，可启动、暂停、继续、审核和重试 |
| StepDefinition | Definition 中的步骤合同；以稳定 `step_id` 标识，输入引用任务端口或上游步骤输出 |
| StepRun | 某个 Task 中对应步骤的一次持久化运行状态，是调度、恢复、进度和错误的事实源 |
| Executor Kind | 平台注册的类型化执行能力；无代码编排可以组合它们，但不能注入任意代码 |
| Resource Binding | 把逻辑端口绑定到具体不可变资源或资源读取边界 |
| Resource Boundary | 冻结某次读取的范围，例如 Dataset 的 `through_seq` 或 Retrieval Snapshot 的 `source_seq` |
| 可编辑流程模板 | 生成流程编辑器初始状态的业务样例；不是 TaskDefinition/Task 之外的第三种运行实体 |
| 人工门（Gate） | 在正式写入、发布或关键判断前由人审核既有步骤产出的通用步骤 |
| Profile | 抽取、检索或分析的版本化配置合同；与 Schema 职责分离 |
| Dataset | 绑定不可变 Schema 的长期数据容器，通过 DatasetBatch 只追加数据 |
| Query Dataset | 从 Base Dataset 增量派生的可检索语义单元，保留源 Item/Asset/Block provenance |
| Retrieval Snapshot | 针对固定 Dataset 边界构建并验证完成的 BM25 + Vector 检索快照 |
| Agent Loop | 模型与受 KnowledgeScope 限制的工具交替执行的循环；无工具调用时自然终止 |
